# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small, self-contained project that animates PaCMAP and LocalMAP (dimensionality reduction algorithms) optimizing a 2D embedding, frame by frame, and renders the result as MP4 video. MNIST is the default dataset; Polis conversations are also supported (see the "Datasets" mechanic below). It captures the embedding at every optimization iteration via the `pacmap` library's public `intermediate_snapshots` kwarg — no forking of the library. The CLI (not the marimo notebook) does make two small, narrowly-scoped monkey-patches: one to capture LocalMAP's evolving far-pair graph (see the LocalMAP caveat below), and one — only when a non-default `--schedule-preset` is asked for — to drive the pair-weight schedule (see "Schedule presets").

## Files

- `pacmap_animation_mnist.marimo.py` — the marimo notebook (interactive, cell-based). This is the primary/reference implementation.
- `pacmap_animation_mnist.cli.py` — headless CLI script that mirrors the notebook's logic. Thin entry point only (PEP 723 header + `main()` call): the actual implementation lives in the `pacmap_cli/` package next to it, re-exported here so `import pacmap_animation_mnist.cli as cli; cli.fit_trace(...)`-style access still works unchanged.
- `pacmap_cli/` — the CLI's implementation, split by pipeline stage: `datasets.py` (`DATASETS`, `load_dataset`, `dataset_meta`, `parse_dataset_spec`, `resolve_color` — which data gets embedded and what colors it, see the "Datasets" mechanic below), `datasets_polis.py` (the Polis loader, lazily imported), `data.py` (`load_mnist`, `resolve_proportion`), `fit.py` (`fit_trace`, `_fit_uncached`), `cache.py` (`fit_key`, `load_fit`, `save_fit` — the on-disk fit cache, see the "Fit caching" mechanic below), `fp_history.py` (`capture_fp_history`, `fp_resample_iterations`, `checkpoint_index_for_frame` — LocalMAP far-pair history, see the caveat below), `camera.py` (`weight_schedule`, `camera_path`), `schedule.py` (`build_schedule`, `PRESETS`, `override_weight_schedule` — the schedule driving the fit, see the "Schedule presets" mechanic below), `pairs.py` (pair subsampling, `compute_edge_alphas`, `pacmap_force`), `overlay.py` (`compute_overlay_text`), `render.py` (`_build_renderer`, `render_animation`, `render_frame`, and the `RENDERERS` backend registry — see the "Renderer backends" mechanic below), `render_fpl.py` (the fastplotlib/GPU backend, lazily imported), `paths.py` (`resolve_output_dir`, `param_tag`, `unique_path`), `config.py` (`DEFAULT_CONFIG`, `parse_args`, `build_config`), `orchestrate.py` (`run_algorithm`, `main`).
- `vendor/valency-anndata` — git submodule backing the `polis` dataset (see the "Datasets" mechanic below). A fresh clone needs `git submodule update --init`.
- `pacmap_animation_mnist.ipynb` — the original Jupyter notebook the marimo version was converted from. Treat as historical reference only; do not edit as the source of truth.
- `tests/` — pytest suite covering `pacmap_cli`'s pure functions plus an end-to-end `main()` smoke test. Run with `uv run pytest`. `tests/_loader.py` loads the entry shim via `importlib` (its filename isn't a valid dotted module path) and adds the repo root to `sys.path` so the shim's own `from pacmap_cli import ...` resolves. `pyproject.toml` pins dependency versions to a known-working set rather than letting a fresh resolution pick incompatible ones (see git history for why).

The marimo notebook and CLI package independently duplicate the same pipeline (fit → replay weight schedule → compute camera path → render). When changing core logic (weight schedule, camera smoothing, rendering), check whether the equivalent change is needed in both.

## Running

Both scripts declare dependencies inline (PEP 723) and run via `uv`/`uvx` without a separate install step:

```bash
# Interactive notebook
uvx marimo edit --sandbox pacmap_animation_mnist.marimo.py

# Headless CLI render
uv run pacmap_animation_mnist.cli.py --algorithm both --n 5000
```

CLI flags: `--dataset` (which data to embed: `mnist` (default) or `polis:<source>` — see the "Datasets" mechanic below), `--color` (what the points are colored by; schemes are namespaced by their dataset, e.g. `polis:n-votes`, and default to the dataset's own), `--n` (subsample size, a fraction in (0, 1] for a proportion of the full ~70,000 points — 1 or 1.0 means all of them, same as passing `all` — or an absolute count), `--algorithm {pacmap,localmap,both}`, `--n-components {2,3}` (embedding dimensionality; `3` fits and renders in 3D — see the "3D rendering" mechanic below), `--n-neighbors`, `--mn-ratio`, `--fp-ratio`, `--low-dist-thres` (LocalMAP only, ignored by PaCMAP: the acceptance distance for the "local" far pairs LocalMAP resamples every 10 iterations — see the LocalMAP caveat below), `--num-iters` (comma-separated PaCMAP phase lengths), `--schedule-preset {vanilla,cycle,breathe}` with `--schedule-period`/`--schedule-mn-min`/`--schedule-mn-max`/`--schedule-fp-min`/`--schedule-fp-max`/`--schedule-fp-phase` (the pair-weight schedule driving the fit; each knob defaults to the chosen preset's own value — see the "Schedule presets" mechanic below), `--seed`, `--n-lines` (also accepts a fraction in (0, 1], as a proportion of each pair type's available pool; 1 or 1.0 means the full pool), `--step`, `--fps`, `--point-size`, `--point-alpha`, `--edge-style-preset {v1,v2}`, `--edge-gamma`, `--line-alpha`, `--fixed-camera`, `--focus-label` (camera tracks one MNIST digit's cluster instead of the whole embedding; pass a digit, or pass with no value to be prompted interactively after MNIST loads), `--zoom` (camera zoom multiplier, default 1.0; >1 frames a smaller radius for finer detail at the cost of cutting off edges, and composes with both `--fixed-camera` and `--focus-label`), `--rotate` (`--n-components 3` only: sweep the 3D camera through one full revolution over the animation instead of a fixed viewing angle; meaningless for a single-frame `--iter` render, which only shows the angle at that one frame), `--iter` (render only one iteration, as a png, or a range of iterations, as an mp4, indexed directly against pacmap's own iteration count rather than the `--step`-derived animation frame — see `render_frame()`/`render_animation()`'s `start`/`end` args; comma-separate multiple values/ranges, e.g. `--iter 50,150,250-400`, to render several outputs from a single fit/trace in one invocation), `--renderer {matplotlib,fastplotlib}` (rendering backend, default `matplotlib`; `fastplotlib` renders offscreen on the GPU, ~2.6x faster — see the "Renderer backends" mechanic below, including the required `uv run --extra fastplotlib python ...` invocation), `--no-cache` and `--cache-dir` (fit caching — see the "Fit caching" mechanic below), `--output-dir`, `--tag-output`, and `--config path/to/config.json` for file-based overrides (CLI flags win over the config file; unset config fields fall back to `DEFAULT_CONFIG` in `pacmap_cli/config.py`).

Renders default to `outputs/` (gitignored) via `resolve_output_dir()` in the CLI script: a relative `--output-dir` value with no `./`/`../` prefix is nested under `outputs/` (e.g. `myrun` → `outputs/myrun`); an absolute path or one starting with `./`/`../` is used as-is. The full layout is **`<output-dir>/<dataset>/[<tag>/]<filename>`**. The dataset slug is *always* a directory level of its own (`outputs/mnist/pacmap.mp4`, `outputs/polis-35bmpjr8um/pacmap.mp4`), including under a custom `--output-dir` (`--output-dir ./out` → `./out/mnist/…`), so there's one rule rather than a special case — and because it's a directory level, the dataset name is *not* in the filename stem (there is no `_mnist` suffix; that layout changed when `--dataset` landed, and old files under `outputs/` were left where they were). This follows the convention the codebase is migrating toward: **algorithm/dataset/fit-identity vars belong in the directory, rendering vars in the filename.** `n_components` and `renderer` predate that rule and are still filename markers; they are deliberately *not* being retrofitted, but anything new lands on the correct side.

`--tag-output` nests the render under a further subdirectory named for whichever params differ from `DEFAULT_CONFIG` (via `param_tag()`/`TAG_PARAMS`), *below* the dataset level, e.g. `outputs/polis-35bmpjr8um/nn5_mnr0.8/`, so a directory listing doubles as a way to compare runs by parameter; `algorithm` and `output_dir` are deliberately excluded from the tag so a `both` run and separate `pacmap`/`localmap` runs with the same other params land in the same folder. `dataset` and `color` are excluded too — the first is a directory level of its own, the second a filename marker. `--iter` is deliberately excluded from the slug as well, since `main()` already bakes it into the output filename directly — `{algorithm}.mp4` by default, `{algorithm}_iter150.png` for a single iteration, `{algorithm}_iter50-300.mp4` for a range — so a tag would be redundant. `n_components` is likewise excluded from `TAG_PARAMS`/the tag slug (it's a pipeline choice, not a "differing tunable param" like `mn_ratio`), but `main()` still bakes a `_3d` marker into the filename when `--n-components 3` — `{algorithm}_3d.mp4` — so a 2D and 3D run with otherwise identical params never collide via `unique_path()`'s `_1`/`_2` fallback. The renderer gets the same treatment: excluded from the tag slug, but non-default backends bake a marker from `RENDERER_FILE_MARKERS` into the filename (`{algorithm}_fpl.mp4` for fastplotlib). A non-default `--color` bakes one too, via `datasets.color_marker()` — `pacmap_colorn-votes.mp4`, the dataset namespace dropped since the directory already carries it — so two colorings of one fit land side by side. The markers compose in the order dimension, renderer, color, iter: `pacmap_3d_fpl_colorn-votes_iter150.png`. `unique_path()` asks before overwriting an existing render; declining appends `_1`, `_2`, etc. instead. `main()` resolves and confirms all output filenames up front, before `load_dataset()`/`fit_trace()` run, so approval happens before any expensive computation rather than after. This output-path logic lives only in the CLI script, not the marimo notebook.

MNIST is loaded via `keras` if available, falling back to `sklearn.datasets.fetch_openml` (pinned to the `liac-arff` parser to avoid a hidden pandas dependency).

The `polis` dataset needs the vendored `valency-anndata` submodule and its optional extra: a fresh clone must run `git submodule update --init`, and (since extras don't apply to PEP 723 script runs) invoke the CLI as `uv run --extra polis python pacmap_animation_mnist.cli.py --dataset polis:<source> ...`.

Tests run with `uv run pytest` (and in GitHub Actions on PRs/main — an environment with no GPU, which is why the fastplotlib canvas tests skip themselves there; see the "Renderer backends" mechanic). There is no linter or build step configured in this repo.

## Architecture / key mechanics

1. **Fitting with full history** — `intermediate_snapshots` must start at 0 (otherwise the internal `itr_ind` counter never binds and a `NameError` results) and have length `sum(num_iters) + 1`. Frame 0 is the initialization; frame *k* is the state after *k* Adam steps. `num_iters` is a 3-tuple of PaCMAP's three optimization phases (neighbor / mid-near / further pairs).

2. **Replaying internals offline** — the pair-weight schedule (`w_MN`, `w_NB`, `w_FP`) and gradients are pure functions of the state already captured, computed via `pacmap.pacmap.find_weight` / `pacmap.pacmap.pacmap_grad` after the fact — nothing needs to be intercepted during the fit. `w_MN` collapsing from 1000 → 3 → 0 across the three phases is the core PaCMAP mechanism: pull global structure into place first, then let the local neighbor term refine it. The CLI can also *drive* that schedule rather than only replaying it — see the "Schedule presets" mechanic below — but only when `--schedule-preset` is non-default; the marimo notebook and the default CLI path still just replay.

3. **Camera** — the embedding expands ~30x over the run. A smoothed, monotonic zoom-out (rolling mean of the 99.5th percentile radius, then `np.maximum.accumulate`) keeps early iterations legible without introducing per-frame jitter. `--fixed-camera` (CLI only) instead locks a single radius sized to the trace's largest extent, trading early-frame legibility (starts as a tiny dot) for an honest view of how much the embedding actually moves. `--focus-label` (CLI only) instead scopes the camera to a single MNIST digit's cluster: both the radius and a smoothed per-frame centroid are computed from just that label's points, so the camera follows the cluster instead of framing the whole embedding from the origin. `--zoom` (CLI only, default 1.0) divides the final per-frame radius after any of the above compute it, so it composes uniformly with `--fixed-camera` and `--focus-label` alike — `--zoom 2` frames half the extent (closer/finer detail, cutting off edges). See `camera_path()` in the CLI script; its center/radius computation is dimensionality-agnostic (operates on `trace`'s last axis regardless of column count), so it needs no changes to support `--n-components 3`.

4. **3D rendering** (`--n-components 3`, CLI only) — `fit_trace()` passes `n_components` straight through to the `pacmap`/`localmap` reducer constructor (default `2`); `camera_path()` and the pair-subsampling/edge-alpha math in `pairs.py` are all dimensionality-agnostic already, so no branching is needed there. Rendering, however, needs a genuinely separate code path: `render.py`'s `_build_renderer_3d()` mirrors `_build_renderer()`'s artist set on top of `mpl_toolkits.mplot3d`'s `Axes3D` rather than branching inside the 2D builder, since the 3D APIs don't overlap with 2D's — 3D scatter is updated via `scat._offsets3d = (...)` (no `set_offsets()` equivalent in 3D), edges use `Line3DCollection` instead of `LineCollection` (added via `ax.add_collection3d(lc, autolim=False)` — `autolim=True`, the default, crashes on the empty initial segments each collection starts with), and the camera additionally frames a `zlim` alongside `xlim`/`ylim`. `render_animation()`/`render_frame()` dispatch to whichever builder matches `n_components`. The 3D camera is fixed at `elev=20, azim=-60` (matplotlib's own defaults) unless `--rotate` is passed, in which case azimuth sweeps linearly through one full revolution over the animation's frame range (`update(f)` calls `ax.view_init(azim=-60 + 360*f/total)`); a single-frame `--iter` render still honors `--rotate` by showing whatever angle that one frame would have in a rotating animation, rather than special-casing it to the fixed default.

5. **LocalMAP caveat** — `--low-dist-thres` (default `10`, `pacmap`'s own) is the one reducer param unique to LocalMAP, passed to the constructor only for `algorithm == "localmap"` (`PaCMAP.__init__` doesn't accept it): it's the acceptance distance bounding which far pairs count as "local" during each resample (and is halved for the phase-3 gradient), so it directly shapes the green edges phase 3 animates. It joins `TAG_PARAMS` as `ldt`. LocalMAP resamples its far-pair graph every 10 iterations after iteration 200, and only the final set survives on the fitted object (`reducer.pair_FP`). Positions are captured fine across all frames regardless. The **CLI** captures the full resample history: `fit_trace()` (`pacmap_cli/fit.py`) wraps LocalMAP fits in `capture_fp_history()` (`pacmap_cli/fp_history.py`), a context-managed monkey-patch of the numba-jitted `pacmap.pacmap.sample_FP_pair_nearby` (called by bare module-level name from `pacmap.pacmap.localmap`, so patching the name is sufficient — no need to duplicate `localmap()` itself) that records each resample's `pair_FP.copy()` and restores the original function afterward, even on exception. `fit_trace()` returns this as `pair_FP_history`, a list of `(frame, pair_FP)` checkpoints (`[(0, pair_FP)]` for PaCMAP, which never resamples, or a LocalMAP run whose phase 3 is too short to trigger a resample); `render.py`'s `_build_renderer()` (and `_build_renderer_3d()`, identically) looks up the checkpoint in effect for each frame via `checkpoint_index_for_frame()`, subsampling far-pair rows once by index (`subsample_pairs_indices()`) so the same source point's edge is tracked across checkpoints as only its target endpoint changes. This monkey-patch is scoped to `pacmap==0.9.1` (pinned in `pyproject.toml`); `capture_fp_history()` asserts the patched function's signature at patch time so an incompatible `pacmap` upgrade fails loudly rather than silently capturing nothing. The **marimo notebook** does not yet have the equivalent change — it still only has the final resampled set — and this is a known deferred follow-up (either port `fp_history.py`'s helpers into the notebook, or have the notebook import from `pacmap_cli` directly).

6. **Rendering** — `matplotlib.animation.FuncAnimation` draws a subsampled set of pairs (colored by type: neighbour/mid-near/further) with opacity driven by the live weight, plus a scatter of points colored by MNIST digit label and a small weight-schedule strip synced to the main frame. Output is written via the `ffmpeg` writer, so `ffmpeg` must be available on `PATH`. Scatter marker size/opacity are `--point-size`/`--point-alpha` (CLI only); lowering `--point-alpha` lets overlapping points blend into visibly denser regions instead of fully occluding each other. Edge width is a single `EDGE_LINEWIDTH` constant (`render.py`, applied by both the 2D and 3D builders) rather than a per-pair-type value — the old 0.5-further/0.7-rest split was never a deliberate encoding, since color already carries pair type. The marimo notebook's copies were flattened to the same 0.5.

   Figure/artist setup and the per-frame `update(f)` closure are factored into a shared `_build_renderer()` helper (CLI only), used by both `render_animation()` (many frames → mp4 via `FuncAnimation`, the default) and `render_frame()` (`update()` called once, then `fig.savefig()` → png). Which one runs is controlled by `--iter` (CLI only): unset renders the full `0`-`sum(num_iters)` range as before; a single value (e.g. `--iter 150`) calls `render_frame()`; a range (e.g. `--iter 50-300`) calls `render_animation()` with `start`/`end` bounding `frames` instead of the default `0`-`total`, still stepped by `--step`. `--iter` indexes directly into `trace` by pacmap iteration number — safe because `intermediate_snapshots` already captures every iteration 1:1, so no rounding is needed. Out-of-range values raise a `ValueError` in `run_algorithm()` before rendering starts. A comma-separated `--iter` (e.g. `--iter 50,150,250-400`) is parsed by `parse_iter_list()` in `pacmap_cli/config.py` into a list of items (`cfg["iter"]`); `fit_trace()` still runs once per algorithm in `run_algorithm()` (`pacmap_cli/orchestrate.py`), which then loops over the items calling `render_frame()`/`render_animation()` once per item against the shared trace, so multiple pngs/mp4s come from one fit rather than refitting per item.

   Edge line opacity per pair type is computed by `compute_edge_alphas()` (CLI only), selected via `--edge-style-preset`. `"v1"` (default) maps each type's alpha from its own raw weight independently — since `w_MN` ranges up to 1000 while `w_NB` (2-3) and `w_FP` (fixed at 1) barely move, mid-near visually dominates phase 1 and further pairs stay near-invisible (alpha capped at 0.05). `"v2"` normalizes the three weights against their per-frame max and raises the ratio to `--edge-gamma` (default 0.2, i.e. strong compression) before scaling by a per-type ceiling (`EDGE_ALPHA_MAX_V2`), so neighbour/further pairs stay visibly present even while mid-near dominates the fit. `--line-alpha` (default 1.0, CLI only) multiplies every line's computed alpha afterward — turn it down when `--n-lines` draws a lot of pairs so overlapping lines don't wash out into a solid wash of color.

   `--n` and `--n-lines` (CLI only) both accept either an absolute count or a fraction in (0, 1], resolved via `resolve_proportion()` as a proportion of the relevant total at the point of use: the full dataset size for `--n` (in `load_mnist()`), or a pair type's available pool for `--n-lines` (in `subsample_pairs()`, called separately per pair type, so e.g. `--n-lines 0.1` draws 10% of neighbour pairs, 10% of mid-near pairs, and 10% of further pairs — each against its own pool size, not a shared one). `1`/`1.0` is inclusive of the upper bound, so it resolves to the full total rather than a literal count of `1`.

   The top-left overlay text is computed by `compute_overlay_text()`, selected via `cfg["overlay_style_preset"]` — a `DEFAULT_CONFIG` field settable only through a `--config` JSON file, not a CLI flag. `"v1"` is the original single line with `w_MN` shown as a float and no `w_FP`. `"v2"` (default) rounds all three weights to integers and stacks them as separate label-aligned lines (`w_MN`/`w_NB`/`w_FP`), so their digits land in the same column frame to frame, making it easier to see the three move together.

7. **Renderer backends** (`--renderer`, CLI only) — rendering is dispatched through a registry in `render.py`: `RENDERERS` maps each backend name to a zero-arg factory returning `{"animation": fn, "frame": fn}`, and the public `render_animation()`/`render_frame()` are thin wrappers that look up `cfg["renderer"]` (default `matplotlib`, the pre-existing code path, unchanged). To add a new backend (plotly and vispy are planned follow-ups for speed comparison): write a `render_<name>.py` module whose two functions accept the same signature, add a factory that lazily imports it, register it in `RENDERERS` and give it a filename marker in `RENDERER_FILE_MARKERS`, and add the argparse choice in `config.py`. Factories must import their backend lazily so `--renderer matplotlib` never touches optional dependencies.

   The `fastplotlib` backend (`pacmap_cli/render_fpl.py`) renders offscreen on the GPU via fastplotlib/pygfx/wgpu and pipes raw frames to `imageio-ffmpeg` — measured ~2.6x faster than matplotlib at the same 770x880 output (render-only, 5000 points, 151 frames: 12.4s vs 32.6s). It's an optional dependency (`[project.optional-dependencies] fastplotlib` in `pyproject.toml`, pinned like the core deps), and extras don't apply to PEP 723 script runs, so the invocation is `uv run --extra fastplotlib python pacmap_animation_mnist.cli.py --renderer fastplotlib ...` (plain `uv run pacmap_animation_mnist.cli.py` won't see the extra); without it installed, a lazy-import guard exits with that hint. It requires a working GPU/wgpu adapter (`RENDERCANVAS_FORCE_OFFSCREEN=1` is set before import so no window system is needed). Both 2D and 3D (`--n-components 3`, `--rotate`) are supported, mirroring the matplotlib artist set: NaN-separated line buffers per pair type with per-vertex RGBA alpha for edges, an orthographic camera driven by the same `camera_path()` output, overlay/legend text in subplot docks, and the weight-schedule strip as a second subplot. Fonts/text are approximate rather than matplotlib-identical (accepted trade-off). Edges and points both set `material.depth_write = False` so semi-transparent geometry alpha-blends instead of depth-culling; the cost is that the GPU then blends them in buffer order, so in 3D `update()` re-sorts both the scatter's point/color buffers and the edge buffer's segments (in blocks of three vertices, by midpoint depth) back-to-front along the view axis every frame — without that, a point or edge passing behind another draws on top of it. All three pair types share a *single* line graphic for this reason: with one graphic per type, layer order beat depth, so a further-pair edge in front of a neighbour edge still drew under it. The merged buffer is laid out in the old layer order (further, mid-near, neighbour) so the unsorted 2D render composites exactly as separate layers did, and matplotlib's zorder does; it also forces one shared `thickness` across pair types, which is why matplotlib's `EDGE_LINEWIDTH` was flattened to match (see below). `DEPTH_SORT_POINTS`/`DEPTH_SORT_EDGES` at the top of `render_fpl.py` turn each sort off (code-level toggles, deliberately not CLI/config flags). 2D needs no sort: everything is coplanar, and buffer order is what matplotlib's single scatter does anyway. Caveats: GPU output is not bit-deterministic, so tests assert on structure/camera state rather than pixel equality, and the canvas tests skip themselves when no wgpu adapter is available (which keeps GitHub Actions green; a lavapipe-based software-rendering CI job is a known follow-up). Tests live in `tests/test_render_fpl.py` and `tests/test_renderer_dispatch.py`.

8. **Fit caching** (CLI only) — a fit is a pure function of the input data and the reducer params (the seed makes it deterministic), so `fit_trace()` caches its result on disk and reuses it when nothing that affects the fit has changed, making render-only iteration (`--n-lines`, `--zoom`, `--edge-style-preset`, `--iter`, `--renderer`, …) skip the fit entirely. On by default, writing to `.cache/fits/` (gitignored); `--no-cache` bypasses both read and write, `--cache-dir` moves it. `fit.py` splits into `_fit_uncached()` (the fit itself) and `fit_trace()` (the cache wrapper around it, which passes `cache_dir=None` straight through to mean "no caching"); the cache itself lives in `cache.py`.

   The key (`fit_key()`) is a blake2b hash of the *actual data array* plus `algorithm`, `n_neighbors`, `mn_ratio`, `fp_ratio`, `num_iters`, `seed`, `n_components`, `low_dist_thres`, `pacmap.__version__`, and — for a non-vanilla `--schedule-preset` only — the schedule params. Hashing `X` rather than `--n`/`--seed` means a different MNIST source (keras vs openml) or a changed loader can't serve a trace fit on other data; including the pacmap version means an upgrade invalidates everything rather than reusing the old implementation's output. `low_dist_thres` is dropped from the key for `--algorithm pacmap`, since PaCMAP ignores it — otherwise varying that LocalMAP knob would needlessly refit the pacmap half of a `both` run. The schedule params get the same treatment under `--schedule-preset vanilla`: that preset leaves the fit unpatched, so its knobs provably can't change the result, and including them would have invalidated every fit cached before the feature existed. `dataset` is likewise absent from the key (it's recorded in `meta.json` for readability only): hashing `X` already makes a Polis fit unable to collide with an MNIST one, and keying on it would have invalidated every fit cached before `--dataset` existed.

   Each entry is a *directory* (`{algorithm}_{key}/`) of plain `.npy` files plus a `meta.json` params sidecar, built in a temp dir and `os.replace()`d into place so an interrupted write can't be read back as a hit (an entry being rewritten is `rmtree`d first, since `os.replace()` won't swap one non-empty directory for another). Arrays are loaded with `mmap_mode="r"` and are therefore **read-only** — verified that nothing downstream writes to a trace or pair array; `update()` rebinds `Y = trace[f]` and every reorder (`Y[order]`, `arr[fp_idx]`) produces a copy.

   The format was benchmarked rather than assumed (`.npz` shipped first). Against `--n all --n-components 3` (379MB trace): npz 1.11s save / 0.99s load, mmap'd `.npy` 0.26s / 0.012s, identical bytes on disk — npz's zip container CRCs every byte both ways, and can't be memory-mapped, so it reads the whole entry into RAM before rendering starts. **Compression is decisively wrong here**: `savez_compressed` took 115s to save that same fit for an 18% size cut, because float32 embedding coordinates are near-incompressible. Don't reintroduce it.

   `pair_FP_history` is deduped: LocalMAP's resample only ever changes a far pair's *target* endpoint (the same invariant `subsample_pairs_indices()` relies on), so the source column is stored once as `fp_sources.npy` with one `fp_targets.npy` row per checkpoint — ~19% off a real entry, measured. `_shared_source_column()` verifies the invariant instead of trusting it, falling back to one verbatim `fp_{i}.npy` per checkpoint if it ever fails. Deduped entries come back as a `_DedupedFPHistory` `Sequence` (not a list) that rebuilds each `(frame, pair_FP)` on access rather than up front, so peak memory stays at one checkpoint (~11MB at `--n all`) instead of the whole history (~280MB) — `render.py` immediately reduces each checkpoint to `n_lines` rows and drops the rest. Anything consuming `pair_FP_history` must therefore stick to indexing/iterating/`len()` and not assume `list`.

   An entry that exists but won't load is treated as a miss (refit and overwritten) rather than an error. **Nothing evicts entries**: a trace is ~2.7MB at `--n 2000` but ~380MB at `--n all --n-components 3`, so clear `.cache/fits/` by hand. `cache`/`cache_dir` are deliberately absent from `TAG_PARAMS`, since they don't change the render. Tests live in `tests/test_cache.py` (the store) and `tests/test_fit_cache.py` (when it refits vs reuses); `tests/conftest.py` chdirs every test into a scratch cwd so the relative default cache dir never lands in the repo.

9. **Schedule presets** (`--schedule-preset`, CLI only) — the pair-weight schedule is normally computed inside the fit by `pacmap.pacmap.find_weight`, one call per iteration. `schedule.py` instead materializes it up front as a `(sum(num_iters), 3)` array of `(w_MN, w_NB, w_FP)`, one row per iteration, and `override_weight_schedule(W)` monkey-patches `find_weight` to serve row `itr`. Both `pacmap()` and `localmap()` call `find_weight` by bare module-level name, so patching the name covers both without duplicating either optimization loop — the same trick `capture_fp_history()` uses, except `find_weight` is plain Python rather than numba-jitted, so its signature guard inspects it directly (no `.py_func`). The two patches compose via an `ExitStack` in `_fit_uncached()`.

   **`vanilla` (the default) never patches anything.** `run_algorithm()` passes `schedule=None` for it, so the default path reaches pacmap exactly as it did before this feature existed — a structural guarantee, not a test-enforced equality. Don't "simplify" this by routing vanilla through the patch with an equivalent array; `tests/test_fit_schedule.py` asserts bit-identity between a vanilla-driven fit and an unpatched one, but the point is that the default run doesn't rely on that.

   The cycling presets sweep two channels between log-spaced bounds every `--schedule-period` iterations, holding `w_NB=2`: **`w_MN`**, the attractive/global channel (`--schedule-mn-min`/`--schedule-mn-max`), and **`w_FP`**, the repulsive one (`--schedule-fp-min`/`--schedule-fp-max`). Both sweeps share `_log_sweep()`; `--schedule-fp-phase` offsets `w_FP` in cycles, defaulting to `0.5` (antiphase) so repulsion troughs exactly when global attraction peaks and the condense/expand halves reinforce rather than cancel. Sweeps are log-spaced because these are scale parameters (even steps are multiplicative, and the meaningful quantity is a ratio like `w_MN/w_NB`), and `cos`-anchored so a run opens at the max rather than mid-sweep. Bounds must be > 0: vanilla's `w_MN = 0` endpoint is at infinite log-ratio distance and isn't a point a continuous sweep can pass through.

   `cycle` and `breathe` are the *same builder with different defaults* — `cycle` sweeps `w_MN` and holds `w_FP` at 1.0, `breathe` holds `w_MN` at 3.0 (vanilla's settled value) and sweeps `w_FP` between 0.2 and 5.0. Either can drive both channels at once by setting the other pair's bounds apart. **`breathe` is the one that actually looks like anything**: measured on a 600-point run, per-cycle radius swing is ×11.6 for `breathe` against ×1.13 for `cycle` — cycling attraction alone changes structure without moving the extent much, because Adam's per-parameter normalization absorbs most of the magnitude change, and extent is dominated by repulsion regardless. Cycling both antiphase gives ×12.9, only marginally better than `breathe` alone.

   Because presets differ precisely by their defaults, `DEFAULT_CONFIG` holds **`None`** for every knob, meaning "whatever this preset wants" — a concrete default there would override every preset back into the same shape. `orchestrate.resolve_schedule_knobs()` merges a preset's defaults (read off its builder's signature via `schedule.preset_defaults()`, so there's no second table to keep in sync) with any explicitly-set flag, and the *resolved* values are what both build the array and enter the cache key — so passing a knob explicitly at its default can't fork a second cache entry for an identical fit.

   Consequences worth knowing. **A non-vanilla preset overrides the weights for every iteration**, so `--num-iters` no longer shapes the schedule at all — it only sets the total iteration count. What `--num-iters` still controls is LocalMAP's phase-3 gating (the `pacmap_grad_nearby_recip_sqrt` gradient and far-pair resampling both trigger on `itr > num_iters[0] + num_iters[1]`, an iteration test independent of the weights), so `--num-iters 0,0,N` puts LocalMAP's contrastive regime in effect for the whole run. For PaCMAP, which has no such gate, `0,0,N` and any other split totalling `N` are the same run. **The default camera fights cycling**: `camera_path()`'s `np.maximum.accumulate` only ratchets outward, so a contraction phase reads as the picture shrinking — `main()` prints a `--fixed-camera` hint rather than forcing it, since `--fixed-camera` is `store_true` with no `--no-` counterpart and so couldn't be overridden. Renderers need no changes: the strip plots `np.log10(W[:, j] + 1)` generically and the overlay reads `W[f]`, both preset-agnostic.

   `run_algorithm()` builds the array **once** and uses it twice — to drive the fit, and as the `W` the overlay/strip display (`np.vstack([S[0], S])`, preserving index == snapshot index). That's the invariant to preserve: deriving `W` from `weight_schedule()` independently would render vanilla weights over a cycle-driven fit. `camera.weight_schedule()` therefore delegates to `build_schedule("vanilla", ...)` rather than keeping its own copy. Adding a preset (chirp, simplex-path) means one new entry in `PRESETS` returning the same array shape; `--schedule-preset`'s argparse choices come from `sorted(PRESETS)`, so it needs no second edit. The **marimo notebook has no equivalent** — it replays vanilla only, a known deferred follow-up alongside the `fp_history` parity gap. Tests: `tests/test_schedule.py` (the builders and the patch), `tests/test_fit_schedule.py` (real fits, bit-identity), `tests/test_orchestrate_schedule.py` (the wiring).

10. **Datasets** (`--dataset`/`--color`, CLI only) — what gets embedded is chosen through a registry in `datasets.py`, built on the same pattern as `render.py`'s `RENDERERS`: `DATASETS` maps a name to a zero-arg factory returning the loader, so an `mnist` run never imports the Polis module or its heavy optional deps. Every loader has the uniform signature `loader(source, n, seed, color)` → `(X, y, rs)` — the contract `load_mnist` already had. `--dataset` takes `<name>[:<source>]`, split by `parse_dataset_spec()` on the *first* colon only, since a source can itself contain them (`polis:hf:user/dataset`, a pol.is URL). `mnist` takes no source; `polis` requires one.

    `dataset_meta(spec, color)` resolves the whole choice — `dataset`, `source`, `slug`, `color`, `cmap` — **without loading anything**, and `load_dataset()` is that plus the loader call. `main()` uses the cheap one first, so a bad `--dataset`/`--color` pairing (or `--focus-label` against a continuous scheme, which would compare a magnitude for equality) fails immediately rather than after a download and a fit.

    **Color is data, not a rendering branch.** Each scheme in `COLOR_SCHEMES` declares its owning dataset and whether it is `categorical` or `continuous`; that collapses to one `cmap` string (`tab10` vs `viridis`) computed once and threaded to the renderers, which stay scheme-agnostic — both matplotlib and fastplotlib normalize a continuous map over the data range themselves. Schemes are namespaced by dataset where they only mean something for one (`polis:group-id`, `polis:n-votes`) and plain where generic (`label`). `DEFAULT_COLORS` picks each dataset's default, so `--color` is optional; a scheme requested for the wrong dataset raises listing what that dataset does support. Adding a dataset = write its loader module, add a `DATASETS` entry, and give it a `DEFAULT_COLORS` entry plus one or more `COLOR_SCHEMES`; `--dataset`'s help and `--color`'s argparse choices are derived from those tables.

    **Polis** (`datasets_polis.py`) embeds a participants × statements vote matrix — points are participants, the standard Polis opinion map (no transpose option). It's backed by the vendored `valency-anndata` submodule, which owns every Polis-specific concern: source parsing (conversation id, report id, `hf:` slug, pol.is URL, local CSV export dir), fetching, rebuilding the matrix from raw vote events, and the imputation/clustering pipeline. `<source>` also accepts the package's **named reference conversations** — `polis:japanchoice:2025_foreign_affairs_security`, `polis:vtaiwan:uber`, `polis:aufstehen` (the ones needing no variant) — dispatched by `_load_source()`: the leading segment is looked up against `val.datasets.__all__` (minus `load`/`translate_statements`, which aren't conversations) and called with the remaining segment as its argument, and anything that isn't such a name falls through to `polis.load(source)` verbatim, so an `hf:user/dataset` slug keeps its colon. The name list is read off the package rather than duplicated, so a dataset added upstream works here after a submodule bump alone. A reference dataset invoked without its required variant raises a `ValueError` naming the flag form, since upstream declares the variant positionally and would otherwise surface a bare `TypeError`. That package can't be a normal dependency — anndata/scanpy and friends conflict with this repo's deliberately tight pins — so it's a git submodule installed through the `polis` extra, and the loader imports it lazily behind a friendly guard naming both `git submodule update --init` and `--extra polis`. **Imputation is the submodule's own** (`recipe_polis` zero-masks meta/moderated statements and imputes statement-wise means, leaving the dense matrix in `layers["X_masked_imputed_mean"]`); it is deliberately not re-decided here. Participants below its 7-vote clustering threshold come back unlabelled and are kept as group `-1` rather than dropped, so the animation still shows everyone. The module's docstring records what was verified about that API, since none of it is guessable from outside.

    The **marimo notebook has no equivalent** — it loads MNIST only, a known deferred parity gap alongside the `fp_history` and schedule-preset ones. Tests: `tests/test_datasets.py` (registry, schemes, slugs, markers — pure), `tests/test_datasets_polis.py` (the real loader against the submodule's own fixture export, skipped when it isn't checked out), `tests/test_datasets_polis_sources.py` (source dispatch against a stub package - pure, so it needs no submodule, extra or network), plus `tests/test_main_smoke.py`'s `synthetic_polis` fixture, which covers load → fit → render with no submodule and no network.
